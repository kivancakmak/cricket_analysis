## Notes
- Step 2: `src/pose.py` uses the MediaPipe Tasks API (mediapipe 1.2.0; legacy `mp.solutions` no longer exists). Smoothing is `smooth_pose()` (One-Euro, numpy only), separate from raw `extract_pose()`. Verified on real clips in `data/raw/` (front-foot defence tutorial, 1920x1080, 25 fps): the two trimmed clips (~100 frames) gave 100% detection, mean visibility 0.94–0.95; the full 2252-frame video gave 84.2% detection, 0.877 visibility.
- Step 3: `src/overlay.py` — `render_overlay()` pipes frames into ffmpeg (libx264, yuv420p, faststart; downscaled to max 1280 px wide) and `export_key_frames()` writes PNGs. ffmpeg is taken from PATH, else from the `imageio-ffmpeg` package (added to requirements; none was installed on this machine). Checked on the trimmed clip: skeleton sits correctly on the batter in a rendered frame. Key-frame labels in the CLI (`--key LABEL=FRAME`) are manual until step 5 detects them. Not yet played in an actual browser.
- Step 4: `src/orientation.py` — `detect_orientation(seq) -> Orientation` (facing, front/back leg, handedness, each with a confidence; low confidence reports "unknown" rather than guessing). Each answer is a weighted vote of cues (nose vs ears, nose vs shoulders, ankle/hip/shoulder order, stride displacement); weights and scales are in `ORIENTATION_CONFIG`. Stance cues use the first 1 s; the stride cue uses the whole clip. Assumes a static camera and orthodox stance (right-hander leads with the left leg). The toe-vs-heel cue is weak side-on (toes point towards/away from the camera) so it has a low weight. Synthetic tests cover both facing directions x both handednesses, no-stride, occluded far side, detection gaps, no detections and an ambiguous pose. On both real trimmed clips: faces right, left leg front, right-handed, confidence 0.86; all strong cues agree. Only one batter has been checked, so left-handers and left-facing clips are tested synthetically only.
- Step 5: `src/phases.py` — `detect_key_moments(seq, orientation) -> KeyMoments` (STANCE, FRONT_FOOT_LANDING, CONTACT, each with frame, time and confidence, plus `notes` for anything that went wrong). Motion is in body-heights/second so it is distance-independent; all thresholds are in `PHASE_CONFIG`. Anchored on the stride (peak forward speed of the front ankle): stance = last still run before it, landing = first run after it where the ankle has stopped forward and vertical motion. **Deviation from the brief for CONTACT:** on both sample clips the peak forward hand speed occurs 0.25–0.35 s *before* the foot lands, so "peak after landing" always picked the first frame of the window. Contact is now the first frame at/after landing where hand speed has dropped to 15% of its peak (hands have arrived). It is still approximate and has no ground truth — tune `contact_release_fraction` against coach labels in step 10. Debug plots: `python scripts/plot_phases.py <videos>` -> `outputs/plots/`. Sample results: clip 1 stance f4 (clip starts mid-stride, conf 0.42) / landing f37 / contact f39; clip 2 stance f39 / landing f65 / contact f73.
- Step 6: `src/metrics.py` — `compute_metrics(seq, orientation, moments) -> Metrics`; each metric is `Metric(value, confidence)`, looked up by name (`head_over_front_knee_{landing,contact}`, `front_knee_angle_landing`, `stride_length_landing`, `balance_{landing,contact}`, `head_stability`, `front_elbow_height_contact`, `spine_tilt_{landing,contact}`). Definitions, units and sign conventions are in the module docstring. Measured on the median pose of ±1 frame around each key moment. Confidence = weakest used joint's visibility × (0.5 + 0.5 × key-moment confidence). Metrics that cannot be computed are omitted and explained in `Metrics.notes`. Hand-built-pose tests cover known answers, both facing directions, left-handers, camera-distance invariance, missing joints/moments. Design choices: head = mean of ears when visible, else nose (nose sits ahead of the head centre in profile); body size = 90th percentile over the clip, because a median is dragged down by the long lunge after the shot (stride came out 1.3 body heights instead of 0.8). Real-clip values look plausible (clip 1: knee 93°, stride 0.81, spine tilt 26°) but are unvalidated against coach judgement. Note: `phases.py` still normalizes velocities by a median body height; harmless but inconsistent with this.
- Step 7: `src/scoring.py` + `rules/forward_defence.yaml`, `rules/front_foot_drive.yaml`. `load_rules(shot)` validates the YAML (every problem reported at once, naming the rule; typos in field names, unknown metrics, bad ranges, missing low/high text all caught) and `score_shot(metrics, ruleset)` returns total /100, 3 category sub-scores, per-rule results (value, score, passed/failed/skipped) and the top 2 fixes ranked by weight × deficit. Rule score = 1 inside the ideal range, falling linearly to 0 over `tolerance`; passed when ≥ `pass_score` (0.9). Rules whose metric could not be measured are skipped (not counted in the score) and lower the confidence instead. A fix/drill may be one text or `{low, high}` wording depending on which side was missed. **All numbers and wording in both YAML files are PLACEHOLDERS – to be set by coaches** (marked in the file header, per rule, and in `RuleSet.status`). Format is documented in the header of `forward_defence.yaml`. Real clips under the forward-defence placeholders: clip 1 = 94/100 (fix: front knee bend 93°), clip 2 = 72/100 (fixes: head movement, head behind knee). Caveat: clip 2's head-stability 0.63 probably includes the batter's forward body travel because landing is detected early (f65) — worth revisiting phase detection with coach labels in step 10.
- Step 8: `src/quality.py` — `assess_quality(seq, orientation, moments, metrics) -> QualityReport`; thresholds in `QUALITY_CONFIG`. Six checks (duration 2–8 s, person detected ≥80% of frames, key-joint visibility using the near-side joint of each pair, no key joint at the image border, camera side-on, key moments/orientation found with enough confidence). All checks always run; `report.instructions` / `report.message` show **root causes only** (e.g. a cut-off foot also lowers ankle visibility and breaks the key moments, but only "Move the camera back so your feet are visible…" is shown). **Deviation on "side-on camera":** the brief's "shoulder width small vs torso height" doesn't fit a cricket side-on view — the shoulder line runs along the pitch, so on the sample side-on clips the shoulder width is 0.4–0.65 of torso length (a front-on or behind-the-batter camera makes it *smaller*, a chest-on one larger). The check therefore rejects shoulder width > 0.9 (chest-on) **and** a sideways foot gap at landing < 0.3 body heights (camera looking down the pitch; sample clips 0.8–1.0). Tested on the clips in `data/raw/`: both trimmed clips pass; the full 90 s tutorial video fails (too long; orientation unclear). No dedicated bad clip was found in `data/`, so I made four bad variants of a trimmed clip (feet cropped off, 1.1 s long, batter cropped at the left edge, dark and blurry) — all rejected with the right instruction. Thresholds are untuned beyond these clips.
- Step 9: `src/pipeline.py` + `app.py`. `analyze(video_path, shot_type, output_dir=None, render=True, on_stage=None) -> AnalysisResult` runs clip-length pre-check -> pose -> orientation -> key moments -> metrics -> quality gate -> scoring -> overlay + key-frame PNGs. It has no UI dependency (a test enforces this); `result.to_dict()` / `to_json()` give a JSON-safe description (NaN -> null, schema_version 1) with `status` of `ok`, `rejected` (friendly "please film again" message, nothing scored) or `error` (unreadable video / missing model); an unknown shot type or broken rules file raises. Clips outside 2–8 s are rejected from the container metadata before any pose work (the 90 s sample is refused in 0.5 s). A good ~4 s clip takes ~6 s on this CPU (pose ~4 s, render ~2 s). `app.py` (Gradio 6; `requirements.txt` now says `gradio>=6` because theme/css moved to `launch()`): video upload or webcam, shot-type dropdown, big score card with confidence and placeholder-rules disclaimer, coloured sub-score bars with text labels, fixes with drills, skeleton video, key-frame gallery, expandable raw metrics / rule table / full JSON, processing time, progress stages, API endpoint `analyze`. Checked in the real UI at desktop and phone width (375 px): a good clip scored 94/100; a clip with feet cut off showed the friendly retry card. 117 tests pass. `.claude/` (local preview config) is git-ignored. Not tested: webcam recording, Hugging Face deployment (step 12), very long processing queues.
- Step 10: **Coach labelling tab** (`labelling_tab.py`, second tab in `app.py`) + `src/labels.py`, `src/agreement.py`, `scripts/agreement_report.py`. A coach enters an ID, loads a clip, sees the AI score card, corrects the three key frames with sliders (frame preview + "AI chose frame N, k frames later (ms)" caption), ticks a box to confirm them, marks each rule Pass/Fail/Skip (AI's verdict and measured value shown under each), gives an overall score and notes, and saves. Re-opening the same clip as the same coach pre-fills their earlier answers. **Only things the coach actually answered are stored** (untouched rules and unconfirmed key frames are not labels, so agreement is not inflated by defaults). `labels/labels.csv` is long format: `timestamp, clip_id, shot_type, coach_id, kind (moment|rule|overall), item, coach_label, ai_label, ai_value, ai_confidence, fps, rules_hash, notes`; saving replaces that coach's earlier rows for the clip, writes atomically, and `rules_hash` records which version of the rules file the AI values came from. `python scripts/agreement_report.py [--shot ..] [--coach ..]` writes `outputs/agreement_report.md`: per-rule accuracy and Cohen's kappa (with AI too-harsh / too-lenient counts), key-moment timing error in ms (positive = AI late), overall score Pearson/Spearman, MAE and bias; samples under 10 are flagged "too few", and mixed rules-file versions trigger a warning. Rendering helpers moved from `app.py` to `ui_cards.py` so both tabs share them. Tried end to end in the browser (load → move slider → pass/fail → save → report); the demo labels were deleted afterwards, so `labels/labels.csv` does not exist yet. **No real coach labels exist yet, so the agreement numbers are untested on real data.** Limits: one clip per labelling (no batch mode), at most 16 rules per shot in the form, clips up to 600 frames, concurrent saves are last-writer-wins.
